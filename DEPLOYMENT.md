# Deploying SA — Vercel + Render + Neon

**SA — Enterprise Operations Platform** · deployment guide for Release 4. Nothing has been deployed by the development
team yet; the current state is recorded in [DEPLOYMENT_STATUS.md](DEPLOYMENT_STATUS.md). Related: [ARCHITECTURE.md](ARCHITECTURE.md) ·
[SECURITY.md](SECURITY.md) · database guide [docs/NEON.md](docs/NEON.md).

```
 Browser ──HTTPS──▶ Vercel (frontend/dist, static SPA)
                     │  /api/*  external rewrite (same origin → first-party refresh cookie)
                     ▼
                   Render web service "nexus360-api" (Docker, Java 21, Spring Boot)
                     │  JDBC over TLS, Flyway migrations at startup
                     ▼
                   Neon PostgreSQL 17           (optional) Redis — shared rate-limit counters
                                                (optional) Anthropic API — SA AI
```

The frontend calls **same-origin `/api`**; `frontend/vercel.json` proxies it to Render. Keeping the API same-origin
means the HttpOnly refresh cookie is first-party, so sessions survive page reloads in every browser — including
Safari, which blocks third-party cookies. (A cross-site alternative is described in [§7](#7-alternative-call-the-api-cross-site).)

Order matters because each service needs the previous one's address: **Neon → Render → Vercel → back to Render
for `FRONTEND_ORIGIN`**. Allow about 30 minutes.

> Secrets go only into the providers' environment settings. Never commit them, paste them into tickets or chat, or
> put them in `VITE_*` variables (those are compiled into the public JavaScript bundle).

## 1. Push the code to GitHub

```bash
cd nexus360
git init            # skip if the folder is already a repository
git add .
git commit -m "SA"
git branch -M main
git remote add origin https://github.com/<you>/nexus360.git
git push -u origin main
```

`.gitignore` already excludes `.env`, build output and test reports. The CI workflow in `.github/workflows/ci.yml`
runs on every push and pull request: backend tests (Java 21, embedded PostgreSQL), frontend build + Vitest, and the
Playwright end-to-end suite including the payroll-outage scenario.

## 2. Neon — database

Full walkthrough with screenshots-level detail: [docs/NEON.md](docs/NEON.md). In short:

1. Create a Neon project (PostgreSQL 17, region close to your Render region — e.g. AWS Singapore for Render Singapore).
2. **Connection details → turn "Connection pooling" off** and copy the **direct** connection string:
   `postgresql://<user>:<password>@ep-xxxx.<region>.aws.neon.tech/neondb?sslmode=require&channel_binding=require`
3. That string is your `DATABASE_URL`. The API converts it to JDBC itself (credentials extracted, SSL kept,
   `channel_binding` dropped because the JDBC driver negotiates it), so no `DATABASE_USER`/`DATABASE_PASSWORD` are needed.

Flyway creates the schema on the first API start (migrations V1–V13, see [DATABASE_SCHEMA.md](DATABASE_SCHEMA.md)); nothing has to
be run by hand. Later releases add new migrations that run on the next start; applied migrations are never edited.

## 3. Render — API

### Option A: Blueprint (recommended)

1. Render dashboard → **New → Blueprint** → select the repository. Render reads [`render.yaml`](render.yaml).
2. Fill in the prompted values (everything marked `sync: false`):

   | Variable | Value |
   |---|---|
   | `DATABASE_URL` | the Neon direct connection string from step 2 |
   | `FRONTEND_ORIGIN` | leave a placeholder such as `https://example.invalid` for now; set it in step 5 |
   | `BOOTSTRAP_ADMIN_EMAIL` | the first administrator's email (see [§6](#6-first-sign-in-and-data)) |
   | `BOOTSTRAP_ADMIN_PASSWORD` | a strong temporary password (≥10 chars, letters and digits); you must change it at first sign-in |
   | `APP_DEMO_PASSWORD` | only if you set `APP_DEMO_SEED=true`; otherwise leave empty |
   | `AI_API_KEY` | only if you enable an LLM (see [§8](#8-sa-ai--llm-provider)); otherwise leave empty |
   | `INTEGRATION_ENCRYPTION_KEY` | optional: `openssl rand -base64 32`. When empty it is derived from `JWT_SECRET` |

   `JWT_SECRET` is generated by Render (`generateValue`).
3. **Apply**. The first build takes ~5 minutes (Maven downloads dependencies inside Docker).
4. When the deploy is live, open `https://<service>.onrender.com/actuator/health` → `{"status":"UP",...}`.

The blueprint uses the **free** plan. Free instances sleep after 15 idle minutes: the first request then takes about a
minute, and the SLA engine (which escalates overdue incidents every minute) is paused while asleep. For real use
switch the service to **Starter** or higher (Render → service → Settings → Instance type).

### Option B: Manual web service

New → Web Service → repository, then:

| Setting | Value |
|---|---|
| Language / runtime | Docker |
| Root directory | `backend` |
| Dockerfile path | `./Dockerfile` (relative to the root directory) |
| Health check path | `/actuator/health/readiness` |
| Instance type | Free for trials, Starter+ for production |
| Environment | the variables in [§9](#9-environment-variable-reference); at minimum `DATABASE_URL`, `JWT_SECRET` (`openssl rand -base64 48`), `FRONTEND_ORIGIN` |

### What the container does

- Builds with `maven:3.9-eclipse-temurin-21`, runs on `eclipse-temurin:21-jre` as a non-root user.
- Heap is sized from the container limit (`-XX:MaxRAMPercentage=75`); the JVM exits on out-of-memory so Render restarts it.
- Listens on Render's `PORT`. Readiness turns `UP` only after Flyway migrations and the database connection succeed,
  so Render never routes traffic to a half-started instance.
- `SIGTERM` triggers graceful shutdown: in-flight requests get up to 25 s to finish.
- Logs go to stdout (Render → Logs). They never contain passwords, tokens or API keys.
- Behind Render's load balancer the client address comes from `X-Forwarded-For` as appended by internal proxies only
  (Tomcat RemoteIpValve), so it cannot be spoofed by the caller.

The startup fails fast — with a clear message in the logs — if `DATABASE_URL`, `JWT_SECRET` (≥32 chars) or
`FRONTEND_ORIGIN` is missing.

## 4. Vercel — frontend

1. Check the Render hostname. If it is not exactly `nexus360-api.onrender.com` (Render adds a suffix when the name is
   taken), edit the first rewrite in [`frontend/vercel.json`](frontend/vercel.json), commit and push:
   ```json
   { "source": "/api/:path*", "destination": "https://<your-service>.onrender.com/api/:path*" }
   ```
   The hostname is public information, not a secret.
2. Vercel → **Add New → Project** → import the repository.
3. **Root Directory: `frontend`**. Framework preset **Vite** (detected). Build command `npm run build`, output
   directory `dist`, install command `npm ci` — all already set in `vercel.json`.
4. **Environment variables: none.** Leave `VITE_API_URL` unset so the app uses the `/api` proxy.
5. Deploy. Note the production domain, e.g. `https://nexus360.vercel.app`.

`vercel.json` also provides the SPA fallback (deep links such as `/incidents/42` load `index.html`), long-lived caching
for hashed assets, security headers (HSTS, `nosniff`, `DENY` framing, referrer and permissions policies) and disables
CDN caching on `/api/*`.

## 5. Connect the two: CORS origin

Render → nexus360-api → Environment → set `FRONTEND_ORIGIN` to the exact Vercel origin (scheme + host, no path, no
trailing slash), e.g. `https://nexus360.vercel.app`. For several origins (custom domain, a stable preview alias)
separate them with commas. Save — Render redeploys.

Wildcards are not supported on purpose. Requests from any other origin receive `403`.

## 6. First sign-in and data

- **Production (no demo data)**: sign in at the Vercel URL with `BOOTSTRAP_ADMIN_EMAIL` / `BOOTSTRAP_ADMIN_PASSWORD`.
  You are asked to set a new password immediately. Then create departments, services, users and SLA policies under
  *Administration*. The bootstrap account is only created when no administrator exists, so you can remove the two
  variables afterwards.
- **Evaluation (demo data)**: set `APP_DEMO_SEED=true` and `APP_DEMO_PASSWORD` (≥10 chars, letters and digits) before
  the first start. The API seeds 9 departments, 28 users, 10 services, 13 knowledge articles, SLA policies, workflows
  and 139 incidents with history — every record flagged **DEMO** in the UI. Demo account emails end in
  `@demo.nexus360.io` and are listed on the login screen. Keep `APP_DEMO_SHOW_PASSWORD=false` on anything public.
  Demo-only tools (payroll-outage scenario, simulated SLA time) operate only on demo records.
- **Adding people**: visitors request access at `/register`; System and IT Admins approve under **Users → Access
  requests** (or use **Invite user**) and receive a single-use invitation link (7 days). Forgotten passwords work the
  same way with a 2-hour reset link. The link is always shown once to the administrator; when SMTP is configured
  (`MAIL_HOST`, see below) it is also e-mailed to the recipient, otherwise deliver it through a trusted channel. Set
  `org.support_email` under Settings → Organisation so `/support` shows it.
- **E-mail (optional)**: set `MAIL_HOST` (and usually `MAIL_PORT`, `MAIL_USERNAME`, `MAIL_PASSWORD`, `MAIL_FROM`) plus
  `APP_PUBLIC_URL` (the web app's public URL, used in links). Without `MAIL_HOST` every message is recorded in the
  outbox as `SKIPPED`, Settings → E-mail and system health show "not configured", and nothing is reported as sent.
  After configuring, send a test message from Settings → E-mail (System Admin) and check the outbox status.
- **Demo data in Release 3**: on top of the base organisation above, the Release 3 seeders add flagged teams, problems,
  changes, releases and deployments, assets, CIs, alert sources and alerts, on-call schedules, major incidents and
  post-incident reviews (described in the "Demo data" sections of [API_DOCUMENTATION.md](API_DOCUMENTATION.md)). The
  record counts quoted above are the Release 2 base figures and were not re-counted for Release 3. On a freshly seeded
  database there is no live payroll outage: the demo payroll major incident is a closed record with a draft review;
  run *Run payroll outage demo* (System Admin) to play the outage through the real engines.

## 7. Alternative: call the API cross-site

If you cannot use the Vercel rewrite (for example the frontend is hosted elsewhere), build the frontend with
`VITE_API_URL=https://<service>.onrender.com/api`, keep `COOKIE_SAME_SITE=None` and `COOKIE_SECURE=true` on the API, and
set `FRONTEND_ORIGIN` to the frontend's origin. Limitation: browsers that block third-party cookies (Safari by default)
drop the refresh cookie, so users there must sign in again after a page reload. The same-origin proxy avoids this.

## 8. SA AI — LLM provider

AI features work without any provider: the deterministic engine classifies, summarises, finds duplicates, recommends
knowledge, proposes root causes and answers analytics questions from live data, and every such answer is labelled
*Deterministic fallback — not AI-generated*. To enable an LLM:

| Variable | Value |
|---|---|
| `AI_PROVIDER` | `anthropic` |
| `AI_API_KEY` | your Anthropic API key (Render secret; never in the frontend) |
| `AI_MODEL` | `claude-opus-5-5` (default) |
| `AI_EFFORT` | `low` (default) — enough for the structured, grounded tasks SA asks for |

Answers produced by the model are labelled with the model name. If the provider fails, times out or refuses, SA
falls back to the deterministic engine and says so in the answer. The Release 3 AI features (problem correlation, CMDB
impact, runbook recommendations, predictive SLA risk, trends) additionally go through a guard: `AI_TIMEOUT_SECONDS` per
attempt, at most one retry, schema validation and a filter that rejects any output containing SQL or shell/cloud
commands. `RATE_LIMIT_AI_PER_MINUTE` caps AI calls per user, which also caps provider cost. Actions the AI proposes that change data (priority
escalation, major declaration, runbooks) go through manager approval and are never applied automatically.

## 9. Environment variable reference

### API (Render)

| Variable | Required | Default | Purpose |
|---|---|---|---|
| `DATABASE_URL` | **yes** | — | JDBC URL or `postgresql://user:pass@host/db?sslmode=require` |
| `DATABASE_USER`, `DATABASE_PASSWORD` | with a JDBC URL without credentials | — | Database credentials |
| `JWT_SECRET` | **yes** | — | HS256 key for access tokens, ≥32 characters. Rotating it signs everyone out |
| `FRONTEND_ORIGIN` | **yes** | — | Comma-separated allowed browser origins (exact match) |
| `PORT` | no | `8080` | Set by Render automatically |
| `DB_POOL_MAX` / `DB_POOL_MIN_IDLE` | no | `8` / `1` | Hikari pool size; keep `DB_POOL_MAX` × instances below the Neon connection limit |
| `ACCESS_TOKEN_MINUTES` | no | `15` | Access-token lifetime |
| `REFRESH_TOKEN_DAYS` | no | `7` | Refresh-token lifetime (rotated on every use); also the lifetime of "remember me" sessions, sliding on every refresh |
| `BROWSER_SESSION_HOURS` | no | `12` | Sign-ins without "remember me": browser-session cookie (no Max-Age) and the session ends this many hours after sign-in (1–72) |
| `COOKIE_SECURE` | no | `true` | `Secure` flag on the refresh cookie; only `false` for plain-HTTP localhost |
| `COOKIE_SAME_SITE` | no | `None` | `None` works same-site and cross-site; `Lax`/`Strict` are fine behind the Vercel proxy |
| `RATE_LIMIT_ENABLED` | no | `true` | Per-IP fixed-window limits |
| `RATE_LIMIT_LOGIN_PER_MINUTE` | no | `10` (`20` in render.yaml) | Sign-in and password-change attempts per IP. Accounts also lock for 15 min after 5 failures |
| `RATE_LIMIT_API_PER_MINUTE` | no | `600` | Authenticated API calls per IP |
| `RATE_LIMIT_INBOUND_PER_MINUTE` | no | `120` | Monitoring-alert webhooks per integration |
| `RATE_LIMIT_AI_PER_MINUTE` | no | `30` | SA AI requests per user per minute (always enforced) |
| `REDIS_ENABLED` / `REDIS_URL` | no | `false` / — | Share rate-limit counters across instances (Render Key Value or any Redis). Not needed for one instance |
| `BOOTSTRAP_ADMIN_EMAIL` / `BOOTSTRAP_ADMIN_PASSWORD` / `BOOTSTRAP_ADMIN_NAME` | no | — | First administrator, created only when none exists; must change password at first sign-in |
| `APP_DEMO_SEED` | no | `false` | Seed the demo organisation (flagged DEMO) on an empty database |
| `APP_DEMO_PASSWORD` | with demo seed | — | Password of all demo accounts |
| `APP_DEMO_SHOW_PASSWORD` | no | `false` | Show the demo password on the login screen |
| `AI_PROVIDER` | no | `none` | `anthropic` or `none` |
| `AI_API_KEY` | with a provider | — | LLM API key |
| `AI_MODEL` | no | `claude-opus-5-5` | Model id |
| `AI_BASE_URL` | no | — | Override the provider endpoint (gateways) |
| `AI_TIMEOUT_SECONDS` | no | `60` | Per-request timeout before falling back |
| `AI_MAX_TOKENS` | no | `8000` | Output budget per request (includes thinking) |
| `AI_EFFORT` | no | `low` | `low`, `medium` or `high` |
| `SLA_SCHEDULER_ENABLED` | no | `true` | Minute-by-minute SLA evaluation and escalation (one instance runs it at a time — PostgreSQL advisory lock) |
| `SLA_EVALUATION_INTERVAL_MS` | no | `60000` | Evaluation interval |
| `WORKFLOW_SCHEDULER_ENABLED` | no | `true` | Runs SCHEDULED workflows (one instance at a time) |
| `WORKFLOW_SCHEDULE_POLL_INTERVAL_MS` | no | `60000` | How often scheduled workflows are checked for a due run |
| `REPORT_SCHEDULER_ENABLED` | no | `true` | Runs due scheduled reports (one instance at a time — PostgreSQL advisory lock; each schedule once per period) |
| `REPORT_POLL_INTERVAL_MS` | no | `60000` | How often scheduled reports are checked for a due run |
| `ALERT_ESCALATION_ENABLED` | no | `true` | Escalates unacknowledged alerts (team-lead policy, or on-call paging when the routed team has a schedule with an escalation policy). One instance at a time — PostgreSQL advisory lock |
| `ALERT_ESCALATION_POLL_INTERVAL_MS` | no | `60000` | How often due alert escalations (and on-call pages) are processed |
| `ALERT_SNS_AUTO_CONFIRM` | no | `true` | Confirm AWS SNS subscription requests for CloudWatch alert sources automatically (only after the SNS signature and topic ARN are verified and the SubscribeURL host is an AWS SNS host) |
| `APP_PUBLIC_URL` | no | first `FRONTEND_ORIGIN` | Absolute web-app URL used for links in e-mails (invitations, password resets, notifications, status page confirmations), e.g. `https://sa.example.com` |
| `MAIL_HOST` | no | — | SMTP server. **Unset = no e-mail**: every message is recorded in the outbox as `SKIPPED`, system health shows `NOT_CONFIGURED`, and nothing is reported as sent |
| `MAIL_PORT` | no | `587` | SMTP port |
| `MAIL_USERNAME` / `MAIL_PASSWORD` | no | — | SMTP credentials (SMTP AUTH is used only when a username is set). Never stored in the database or returned by the API |
| `MAIL_FROM` | no | `MAIL_USERNAME` when it is an address, else `no-reply@<MAIL_HOST>` | Sender address (display name "SA") |
| `MAIL_STARTTLS` | no | `true` | Use STARTTLS when the server offers it |
| `MAIL_OUTBOX_ENABLED` | no | `true` | Runs the outbox delivery scheduler (row locks — safe with several instances) |
| `MAIL_POLL_INTERVAL_MS` | no | `30000` | How often due outbox messages are sent |
| `MAIL_MAX_ATTEMPTS` | no | `5` | Delivery attempts before a message becomes `FAILED` (backoff 30 s, 1, 2, 4 … min, at most 1 h) |
| `INTEGRATION_ENCRYPTION_KEY` | no | derived from `JWT_SECRET` | AES-256-GCM key (base64, 32 bytes) for stored webhook secrets. Changing it makes stored secrets unreadable |
| `INTEGRATIONS_ALLOW_PRIVATE_TARGETS` | no | `false` | Allow webhooks to private/loopback addresses (SSRF guard). Keep `false` in production |
| `SWAGGER_ENABLED` | no | `true` | Serve `/swagger-ui.html` and `/v3/api-docs` |
| `SERVER_TOMCAT_REMOTEIP_INTERNALPROXIES` | no | private ranges | Regex of proxies trusted to append `X-Forwarded-For` |

Settings that are **not** environment variables: approval-deadline escalation (`app.approvals.scheduler-enabled`,
`app.approvals.escalation-poll-interval-ms`, default on / 60 s), workflow retry polling (`app.workflow.retry-poll-interval-ms`,
15 s) and the SSE keep-alive (`app.notifications.ping-interval-ms`, 25 s) are Spring properties with defaults in code or
`application.yml`; they can be overridden like any Spring property if ever needed. Business rules such as duplicate
thresholds, alert grouping and escalation minutes, `ai.sla_risk.history_days` or `pir.due_days` are **system settings**
stored in the database (Settings in the UI), not environment variables — see [DATABASE_SCHEMA.md](DATABASE_SCHEMA.md).

There are no separate environment variables for on-call, major incidents or post-incident reviews: they use the
alert-escalation, e-mail and AI settings above.

## 10. Post-deployment verification

Run these against the live URLs — a deployment is only "done" when they pass.

```bash
API=https://<service>.onrender.com
WEB=https://<project>.vercel.app
curl -s $API/actuator/health/readiness              # {"status":"UP"}
curl -s $WEB/api/health                             # via the Vercel proxy: {"status":"UP","database":"UP",...}
curl -s -o /dev/null -w "%{http_code}\n" $WEB/api/incidents                        # 401 (auth enforced)
curl -s -o /dev/null -w "%{http_code}\n" -X POST $API/api/auth/login \
     -H "Origin: https://evil.example" -H "Content-Type: application/json" -d '{}'  # 403 (origin rejected)
curl -s -o /dev/null -w "%{http_code}\n" $WEB/incidents/1                          # 200 (SPA deep link)
```

In the browser:

- [ ] `/` shows the landing page with **System Operational** (live `/api/health`); Enter Workspace → `/login`.
- [ ] Request access at `/register`, approve it under Users → Access requests, open the invitation link in a private
      window, set a password and sign in; the link fails the second time.
- [ ] Sign in; reload the page — you stay signed in (refresh cookie works).
- [ ] Command Center shows live counts; *API Connected* in the sidebar.
- [ ] Create an incident, reload, it is still there; its SLA countdown runs.
- [ ] As an employee, admin pages show *Access restricted*.
- [ ] SA AI answers carry a source label (model name or *Deterministic fallback*).
- [ ] Settings → E-mail shows the real state (configured and a test message SENT, or "not configured" and messages SKIPPED).
- [ ] Integrations, alert sources and CI/CD sources are only described as working once a real delivery shows
      `PROCESSED` in their delivery log.
- [ ] Audit Logs (admin/auditor) list your sign-in and the incident creation.
- [ ] DevTools → Application → Cookies: `nexus_refresh` is `HttpOnly`, `Secure`, path `/api/auth`.
- [ ] No API keys or secrets in the JS bundle (`grep` the downloaded `assets/*.js` for your key prefixes).

## 11. Troubleshooting

| Symptom | Cause and fix |
|---|---|
| Render deploy fails: `JWT_SECRET must be at least 32 characters` / `DATABASE_URL` unresolved | Variable missing or too short — set it in Environment and redeploy |
| `FATAL: password authentication failed` / `connection refused` | Wrong or pooled Neon string; copy the **direct** string again (pooling off) |
| Health check times out on the first deploy | Free instance cold start or Neon waking from suspend; wait and redeploy once. Starter instances avoid it |
| Login works but every call returns `403` | `FRONTEND_ORIGIN` does not exactly match the browser origin (scheme, host, no trailing slash) |
| Signed out after every reload | The app is calling the API cross-site and the browser blocks the cookie — use the Vercel `/api` rewrite and leave `VITE_API_URL` unset |
| `/api/...` on Vercel returns 404 or 502 | The rewrite destination in `vercel.json` does not match the Render hostname, or the API is asleep/crashed |
| `429 Too many sign-in attempts` | Per-IP login limit; raise `RATE_LIMIT_LOGIN_PER_MINUTE` if many users share one network |
| AI answers always say *Deterministic fallback* | `AI_PROVIDER`/`AI_API_KEY` unset, or the provider failed — the answer's notice gives the reason |
